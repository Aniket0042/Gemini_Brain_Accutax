# Session context, model picker and weekly reports: plan

Status: approved to start, 11 Oct 2026. Phase 1 deployed 11 Oct (1706295). Phase 2 deployed 11 Oct with Sonnet 5 only (3750dd8; neither Haiku passed). Next: Phase 3, weekly reports.
Scope: the agent path (`agent/loop.py`, `agent/preview.py`), the Cube model in `semantic/`, and the chat frontend.

## 1. Order and why

1. **Session context first.** It fixes a failure users hit today and is the cheapest of the three. The other two depend on it: a scheduled report opens a chat thread, and follow-up questions in that thread need context.
2. **Model picker second.** Small build, but each model needs an eval run before release. Reports store a model choice, so the picker comes before them.
3. **Weekly reports last.** Largest piece: a scheduler, Cube rollups, two new tables (DBA go-ahead) and finance sign-off.

## 2. What the code does today (verified 11 Oct 2026)

- The agent sends only the last 6 messages, as plain text (`MAX_HISTORY_MESSAGES` in `agent/loop.py`, `HISTORY_MESSAGES` in `agent/preview.py`). Tool calls are not saved: no view, measures, filters, period or organizations.
  - The baseline (section 3, 1.1) shows the model rebuilds the earlier query from the answer text well inside those 3 turns. Anything older is lost.
- Each session already has a `conversation_state` JSONB column. Today it holds only the context meter. It can hold structured context with no DDL.
- The verifier checks figures only against this turn's tool results. A follow-up that quotes a figure from an earlier turn gets flagged.
- `GET /models` returns one entry with `picker_hidden=True`. The frontend picker was deleted in ffa7de2. Wave 3b planned to remove `/models`; **that part of wave 3b is cancelled**, because the picker reuses the endpoint.
- There is no scheduler, and the Cube model has no `pre_aggregations`. `artifacts/` already has `report_spec.py`, `facts.py`, `insights.py`, `narrator.py` and PDF output, which the reports work reuses.
- The replay harness (`scripts/eval/replay_real_questions.py`) replayed follow-ups only for multi-organization cases; single-organization follow-ups ran without a thread. Fixed in 1.1.

## 3. Phase 1: session context (about 1 week)

Phase 1 was re-ordered on 11 Oct after the baseline (1.1). The agent already carries context well inside the last three turns. It fails in three places: turns older than the 6-message window, files and charts asked for in a follow-up, and unclear requests. The steps below fix those first. The per-turn structured context planned before is now a fallback (1.6).

### 1.1 Follow-up test set and baseline — done 11 Oct

**Set.** `tests/data/followup_chains.json`: 32 chains, 83 turns, 51 follow-ups, generated by `scripts/eval/build_followup_chains.py`.
- 23 chains written by hand: period, breakdown, entity ("the top one", "the second one"), share of an earlier figure, scope, file, clarify, topic switch, long thread.
- 9 chains replay real threads from the chat history (orgs 24–33, 27 Sep – 10 Oct). Real history has few true follow-ups: most threads are independent questions asked one after another. The 5 "independent" chains check that a new question does not inherit the earlier turn's filters or period.
- The harness gives every case a thread and checks each turn: `carry` (the tool call the turn should make; no call is accepted where the earlier answer already holds the figures), `asks` (asked instead of guessing), `file` (the app would attach the file or chart).

**Baseline.** Three runs on the VM against the deployed agent (87dd10a, Sonnet 5 plans and writes), eval copy `/tmp/agent_eval_ctx`. Graded by hand; the automatic `carry` check agrees after the spec fixes.

**Failures, each seen in all three runs:**
- **f26f, long thread.** "Go back to the revenue figure from my first question and compare it with the quarter before." Turn 1 is outside the 6-message window. The agent compared this month's net sales with Q3. In run 3 it also stated that the first question had been about this month, which is false.
- **f19b and f20b, files.** "Add net profit to it" after an Excel request, and "same for last year" after a chart request, get no file or chart. The app decides delivery from the current message only (`preview.attachment`, `artifacts/delivery.detect_delivery`).
- **f22b, unclear request.** "Fix it" re-ran the query and answered "Confirmed — the figures were correct" (run 3: "Here's the corrected comparison"), with nothing to fix. "What about the other one?" (f21b) got a clarifying question in all runs.

**Also seen:** in 9 of 9 cases where the figures were already in the earlier answer (f07b, f13b, f27c), the agent answered from that text without a new tool call, with correct figures. The verifier does not see those figures, so it would flag them if it enforced.

### 1.2 Token-budgeted history (fixes f26f)

- Replace the fixed 6 messages with a token budget: 24K for history, per `USAGE_LIMITS_DESIGN.md`. Newest turns first, whole turns only.
- When the thread passes 80% of the budget, compact the oldest turns into a summary that keeps the questions and the query specs (view, measures, period, filters) but not the figures, which are fetched again.
- Prompt rule: never state what an earlier question was unless it is in the history or the summary. Say it is no longer available and ask.
- Applies in `agent/preview.py` (history read) and `agent/loop.py` (`_messages`). The context meter (`memory/context_window.py`) then shows real fullness.

### 1.3 Keep file and chart requests in follow-ups (fixes f19b, f20b)

- Save the delivery of each turn (format, chart or file) in `conversation_state`.
- A follow-up that changes the query ("add X to it", "same for last year", "now by quarter") and does not name a new delivery keeps the last one. A new standalone question does not.
- The model is told what will be attached (`attachment` in the system prompt), as today.

### 1.4 Ask when the request is unclear (fixes f22b)

- Prompt rule: when the request does not say what to change or which item it means ("fix it", "the other one" with no candidates), ask one short question and do not call tools.
- Never say figures were corrected unless a different query produced different figures.

### 1.5 Earlier figures as verifier evidence

The results of the last few turns' figure tools are kept with the turn and passed to the verifier as earlier-turn evidence, so answers that reuse earlier figures (9/9 in the baseline) are checked, not flagged.

### 1.6 Structured per-turn context (fallback)

Only if 1.2 does not fix the long-thread case: a compact record per turn in `conversation_state.turns[]` (tool, view, measures, filters, period, entities, files), shown to the model as an "Earlier in this chat" block. The compaction summary in 1.2 already carries the query specs, so this may not be needed.

### 1.7 Security rule

Tenant scope always comes from the request, never from stored context or the summary. If the user switches organizations in a thread, earlier figures are marked as another organization's and their queries are never re-run on the old organization. An isolation test covers this.

### 1.8 Exit check

- Follow-up set, three runs: carry 144/144 (f26f fixed), file 6/6, asks 6/6. No new misses elsewhere.
- Real (89) and golden sets no worse than 78/11/0 and 66/8/2, over three runs.
- p95 latency up by no more than 2 s; cost per run of the follow-up set no more than about $1.60 (longer history costs input tokens).

### 2.2 Backend

- A model registry in settings: key, label, planner model, writer model, price tier, allowed users or roles.
- `/models` returns the list with `picker_hidden=False`.
- The server checks `selected_model_key` against the registry. The client never sends a raw Bedrock model ID.
- The chosen model goes to `run_agent(model_id, answer_model_id)`. It is the same agent; the picker only changes which model plans and writes.
- VAT law answers keep their fixed model (recommended), because they already vary between runs.
- New models added to `config/pricing.py`.

### 2.3 Save and show the choice

The model key is stored in `conversation_state`; the answer shows "Answered by X"; `answer_log` records the model.

### 2.4 Frontend

Dropdown in the composer, disabled while an answer runs; the last choice remembered in localStorage; labels Balanced / Fast / Cheapest with a cost hint. Check the leftover code at `App.jsx:291` and `App.jsx:1062`.

### 2.5 Cost guard

Until usage limits are built, expensive models sit behind an allowlist (like `AGENT_PREVIEW_USERS`). Usage limits then charge credits from each model's real cost.

## 5. Phase 3: weekly reports (about 3–4 weeks)

Cube's paid Scheduled Tasks (changelog, 10 Jul 2026) save an agent prompt with a cadence, run under the creator's security context, update reports, email the workspace, and open a chat thread per run for follow-ups. We copy that, with one addition for finance quality: numbers come from code, not from the model.

### 3.0 Spec and sign-off (before build)

- "Weekly Business Review": sales, purchases and P&L for the week against the previous week and the same week last year; receivables aging and the top 10 overdue; payables due next week; cash position and the 13-week forecast; VAT accrued quarter to date; low-stock items.
- Week is Monday to Sunday in the organization's timezone; sent Monday 08:00.
- Finance signs off the metric definitions. Still open: ledger P&L against documents, and revenue left on cancelled invoices.

### 3.1 Fixed-spec report engine

Each section is a fixed set of Cube queries (on `report_spec.py`, `facts.py`, `insights.py`). Code computes every change and percentage. The model (`narrator.py`) writes only the commentary and cites the figures it was given. The verifier runs with `enforce=True`: a report with an unsupported figure is not sent.

### 3.2 Cube rollups

Weekly `pre_aggregations` per organization for sales, purchases, P&L and VAT, in Cube Store, refreshed off-peak, so Monday runs do not scan the shared primary database. Parity test rollup against raw over 12 weeks for the test organizations. Check VM disk and memory first.

### 3.3 Storage (needs DBA go-ahead)

Tables `report_schedules` and `report_runs`: owner, organizations, spec, model key, cadence; status, PDF path, thread id; a unique key on (schedule, week) so retries never send twice. PDFs stay on the local disk store.

### 3.4 Scheduler

A systemd timer and a worker command on the VM, not a scheduler inside the API (which would run once per worker). Each run checks the owner still has access to each organization (if not, it skips and disables the schedule), mints a Cube token for those organizations, retries with backoff, and spreads organizations over time.

### 3.5 Delivery

Each run creates a chat thread; the report is the first assistant message with KPI tiles, charts and the PDF. Follow-ups work because of Phase 1. Email later, as a link rather than an attachment; SES or SMTP to be decided.

### 3.6 UI

A "Schedule weekly" button on report answers; a schedules page with list, pause, run now and history.

### 3.7 Saved-prompt tasks

A user saves any agent question as a weekly task, run through the agent with relative dates. Labelled "AI-generated", because it has weaker guarantees than the fixed report.

### 3.8 Quality bar before release

Golden reports for orgs 24 and 25 hand-checked against the Accutax screens; every figure reconciled against Cube directly; four weekly runs in a row reviewed on the VM. Seed orgs 26–33 are not used for demos (their ledger revenue is negative).
